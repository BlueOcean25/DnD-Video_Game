# DnD-Video Game

## Updates

The current game version is `v0.5.7-alpha`. It is shown in the corner of the page. The page checks the server version on connection and periodically while open. If a newer server version is available, a reload banner appears over the login page or game. After a server reconnect, signed-in players need to log in again. For each release, update `GAME_VERSION` in `backend/main.py`, `APP_VERSION` in `frontend/index.html`, and the visible version label to the same version.

## Accounts

Install the backend dependencies with `pip install -r backend/requirements.txt`, then run the backend with `python backend/main.py`. For persistent hosted accounts, create a private PostgreSQL database (for example, on Neon) and set its connection string as `DATABASE_URL` in `backend/.env` or as an environment variable in the backend's hosting service. An environment variable takes precedence over the `.env` value. The backend reads `backend/.env` directly; no dotenv package is needed. Do not put the connection string in source control or expose it to the browser. On its first start with `DATABASE_URL`, the backend creates its tables and imports existing accounts from `backend/account.csv` and reset codes from `backend/codes.csv` once. Every other CSV in `backend/` is discovered automatically and stored in its own Neon table, with columns based on its CSV header. Neon is authoritative: startup refreshes registered local CSV files from Neon, and password changes or resets refresh the account CSV.

To deliberately send local CSV changes to Neon, run `python backend/main.py --push-csv-to-neon` from the repository root. The command reads `DATABASE_URL` from `backend/.env` (or the environment variable, if set). It updates or adds accounts matched by name or username without deleting other Neon accounts. For each other CSV in `backend/`, it creates or updates a separate Neon table and replaces that table's rows with the complete local file. Table names use the `csv_<filename>_<suffix>` pattern; `csv_file_registry` maps table names to filenames. New CSVs are included automatically on the next push. Removing a local CSV does not delete its Neon table; this avoids accidental data loss. If a CSV header changes, new columns are added and old unused columns are retained in Neon, while the CSV uses its current header. After pushing, local registered CSVs are refreshed from Neon. Run the push before starting/restarting the backend, because startup automatically pulls Neon data into the CSVs and can overwrite unpushed local edits. `codes.csv` and `account.csv` are handled separately; reset codes remain in the database because the codes are secrets. A hosting service may use an ephemeral filesystem, so keep an independent backup if you need durable local CSV copies. Without `DATABASE_URL`, the backend continues to use the local CSV files; `ACCOUNT_FILE` and `CODES_FILE` can override their paths.

Signed-in players can open **Settings** in the game to change their password. They must enter their current password and choose a new password between 8 and 72 UTF-8 bytes. Passwords are stored as bcrypt hashes in the configured account CSV or in the PostgreSQL `accounts` table.

The reset flow selects an account by its name and saves a one-time code to `backend/codes.csv` (or `CODES_FILE`) in CSV mode, or to the PostgreSQL `password_reset_codes` table when `DATABASE_URL` is configured. The code is not returned to the browser; in database mode an administrator must retrieve it through a trusted database console and send it to the account owner. Reset codes are stored as plain text, so restrict database/file access and verify the requester before sharing a code.

The backend uses `websockets` for game connections and serves HTTP health checks separately: `GET` and `HEAD` requests to `/healthz` return `200 OK` (and `/` remains supported). Health checks do not require a WebSocket upgrade. The game server must still run on a host reachable by players; a database preserves accounts but does not keep the game server online. Three.js remains loaded from its CDN in the browser. The backend writes timestamped server and player activity events to `backend/server.log` and also prints them to the console. The log rotates at 1 MB and keeps three backups (`server.log.1` through `server.log.3`), for a maximum of about 4 MB total. It records connection, login, game-entry, and password-reset events, but never logs passwords or reset codes.
